UNIVERSITY TEAM PROJECT

Paruzzel

A first-person 3D puzzle game developed in a team of five. The game is built around puzzle rooms that exist in two different dimensions, allowing the player to switch between different versions of the same environment.

Role Gameplay Programmer
Engine Unity
Language C#
Team 5 Developers
Format 3D · First Person

OVERVIEW

A puzzle game across two dimensions

Paruzzel is a first-person puzzle game in which each room can exist in two different dimensions. Switching dimensions changes parts of the environment and creates different ways to solve each puzzle.

Puzzle elements include movable cubes, pressure plates, electrical systems and teleporters. Objects and routes can behave differently depending on the currently active dimension.

My programming work focused on the player side of the game: first-person movement, interaction detection and physically picking up and carrying puzzle objects.

FIRST-PERSON CONTROLLER

Responsive 3D player movement

Paruzzel was my first 3D game project and required a different approach to player movement compared with my previous 2D games.

The player controller uses Unity's CharacterController and handles movement, sprinting, jumping and first-person camera rotation.

Ground and air movement use different acceleration values, while jumping includes a short jump buffer and coyote time to make the controls more forgiving.

Why use CharacterController?

I moved away from a Rigidbody-based controller to gain more direct control over movement and jumping. This made it easier to tune acceleration, gravity and ground detection, resulting in more consistent and responsive first-person movement.

Ground and air movement

Horizontal movement uses different acceleration values depending on whether the player is currently grounded. 

private void MoveHorizontal(bool grounded)
{
    var currentSpeed =
        _isSprinting
            ? speed * sprintMultiplier
            : speed;

    var wishDir =
        (
            transform.forward * _movementInput.y
            + transform.right * _movementInput.x
        ).normalized;

    var targetVelocity =
        wishDir * currentSpeed;

    var accel =
        grounded
            ? groundAcceleration
            : airAcceleration;

    var newSpeed =
        Mathf.MoveTowards(
            _horizontalVelocity.magnitude,
            targetVelocity.magnitude,
            accel * Time.fixedDeltaTime
        );

    _horizontalVelocity =
        wishDir.sqrMagnitude > 0.0001f
            ? wishDir * newSpeed
            : Vector3.MoveTowards(
                _horizontalVelocity,
                Vector3.zero,
                accel * Time.fixedDeltaTime
            );
}

Buffered jumping

Jump input is remembered briefly and can still trigger shortly after leaving the ground, making the controller more forgiving without changing the visible rules of the game. 

private bool CanJump =>
    Time.time - _lastGroundedTime
        <= coyoteTime
    &&
    Time.time >=
        _lastJumpTime + jumpCooldown;


private bool HasBufferedJump =>
    _jumpRequested
    &&
    Time.time - _jumpRequestedTime
        <= jumpBufferTime;


private void HandleJump()
{
    if (!HasBufferedJump)
        return;

    if (!CanJump)
        return;

    _jumpRequested = false;

    _verticalVelocity =
        JumpVelocity;

    _launchVerticalVelocity =
        _verticalVelocity;

    _lastJumpTime =
        Time.time;
}

PLAYER INTERACTION

Detecting and interacting with puzzle objects

Player interaction is based on raycasts originating from the first-person camera.

The raycasting system provides information about the object the player is currently looking at. Other player systems can then use that information to decide whether the object can be interacted with or picked up.

This keeps object detection separate from the behaviour that actually performs an interaction.

Why separate detection from interaction?

Multiple gameplay systems need to know what the player is currently looking at. Keeping the raycasting logic independent prevents each interaction mechanic from performing its own separate detection.

Raycasting Interaction Layer Masks First-Person Gameplay

Camera-based detection

Raycasts start slightly in front of the camera and search for objects within the player's interaction range. 

var origin =
    cameraTransform.position
    + cameraTransform.forward * 0.2f;

var direction =
    cameraTransform.forward;


if (Physics.Raycast(
        origin,
        direction,
        out var hit,
        range,
        mask,
        QueryTriggerInteraction.Ignore))
{
    var result =
        new RaycasterResult(
            Time.time,
            hit.point,
            hit.collider.gameObject
        );
}

OBJECT PICKUP SYSTEM

Carrying physics-based puzzle objects

Certain puzzle objects can be picked up and carried in front of the player.

Instead of directly attaching the object to the camera, the grabber calculates a target position in front of the player and moves the object's Rigidbody toward it using a spring-like force and damping.

If the object moves too far away from the hold position, it is automatically dropped. Held objects also use a dedicated physics layer to prevent collisions with the player's collider.

Why keep Rigidbody movement?

Puzzle objects still need to behave as physical objects while they are carried. Moving them toward a target position allows them to follow the player smoothly while still keeping the pickup system connected to Unity's physics simulation.

Rigidbody Physics Pickup System Damping Collision Layers

Physics-based object holding

The held Rigidbody is continuously moved toward a target position in front of the camera using a spring force and velocity damping. 

Vector3 targetPosition =
    cameraTransform.position
    + cameraTransform.forward
        * holdDistance
    + Vector3.up
        * holdHeightOffset;


Vector3 toTarget =
    targetPosition
    - rb.position;


Vector3 springForce =
    toTarget
    * followStrength;


Vector3 dampingForce =
    -rb.linearVelocity
    * damping;


Vector3 newVelocity =
    rb.linearVelocity
    +
    (
        springForce
        + dampingForce
    )
    * Time.fixedDeltaTime;


rb.linearVelocity =
    Vector3.ClampMagnitude(
        newVelocity,
        maxHoldSpeed
    );

DEVELOPMENT TOOL

Freecam for testing puzzle rooms

I also implemented a developer freecam that temporarily disconnects the camera from the normal player controller.

While active, the camera can fly freely through the environment. The normal CharacterController and movement component are disabled until the player returns to standard gameplay.

The tool can also move the player's return position, which made it useful for quickly reaching and testing different areas of a puzzle room.

Why build a freecam?

Testing a puzzle level often requires repeatedly reaching specific positions. A free camera reduced the time needed to move through already completed parts of a room while debugging.

Debug Tools Freecam Camera Control Development Workflow

Switching between player and freecam

Entering freecam stores the player's state, disables normal movement and detaches the camera pivot. Exiting restores the original player controller. 

private void EnterFreecam()
{
    _savedPlayerPosition =
        transform.position;

    _savedPlayerRotation =
        transform.rotation;

    _freecamPosition =
        cameraPivot.position;


    if (_cc != null)
        _cc.enabled = false;

    if (_playerMovement != null)
        _playerMovement.enabled = false;


    cameraPivot.SetParent(
        null,
        true
    );

    _active = true;
}

MY ROLE IN THE TEAM

Programming and early project coordination

At the beginning of the project I also took on organisational responsibilities alongside programming. I helped coordinate meetings, structure early planning and participate in gameplay and project decisions.

As development progressed, my main technical responsibility became the player-side systems shown above.

Other systems in Paruzzel, including major parts of the underlying event architecture and several puzzle mechanics, were implemented by other members of the team and are therefore intentionally not presented here as my own technical work.

PROJECT TAKEAWAYS

What I learned from working in a team

Paruzzel was my first larger development project in a team of five and my first time building a 3D game.

The project introduced me to working with a shared Git repository, feature branches, merge conflicts and dividing development work into separate tasks.

I also learned that technical work is only one part of a team project. Planning, communication, keeping responsibilities clear and consistently following through on agreed tasks are just as important.

Especially toward the end of the project, balancing university workload and project responsibilities showed me the importance of communicating problems early instead of allowing work to accumulate.

That experience changed how I approach collaborative projects: I now place more emphasis on clear responsibilities, smaller tasks and communicating blockers before they become larger problems.
